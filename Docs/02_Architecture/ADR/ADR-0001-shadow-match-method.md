# 그림자 일치 판정 방식

## 맥락
게임의 핵심은 "플레이어가 만든 그림자가 벽의 목표 그림자와 같은가"를 판정하는 것이다. 판정이 불안정하면(조금 어긋났는데 통과, 거의 맞는데 실패) 퍼즐 경험 전체가 무너진다. M1 수직 슬라이스 전에 방식을 정해야 한다.

## 고려한 대안
| 대안 | 장점 | 단점 |
|---|---|---|
| A. 트랜스폼 판정: 오브젝트의 위치·회전이 목표값(광원 기준)과 허용 오차 안이면 일치 | 단순·결정적, EditMode 테스트 쉬움, 성능 비용 거의 0, 디자이너가 SO로 튜닝 | 서로 다른 배치가 같은 그림자를 만드는 경우(대칭·거리-크기 트레이드오프)를 따로 처리해야 함 |
| B. 실루엣 비교: 광원 시점에서 오브젝트를 마스크 RenderTexture로 그려 목표 마스크와 IoU 비교 | "보이는 그대로" 판정, 대칭 문제 자동 해결 | GPU readback(비동기) 필요, 해상도·임계값 튜닝 어려움, 테스트 어려움, 구현 비용 큼 |
| C. 하이브리드: A로 후보를 거르고, 근접 시 B로 최종 확인 | 정확도 높음 | 두 시스템 유지 비용 |

## 결정
**A(트랜스폼 판정)** 로 시작한다. 이 게임은 페이지당 그림자 2~4개, 오브젝트도 디자이너가 정한 것이라 "정답 배치"를 SO에 저장할 수 있다. 대칭은 `ShadowTargetData`에 대칭 축/각도 목록을 두어 처리하고, 광원 방향 축(깊이)의 오차는 크기 변화로 이어지므로 깊이와 평면 오차를 따로 둔다. 배치 감각을 돕기 위해 목표 근처에서 스냅(자석) 보정을 넣는다.

## 언리얼과 비교
언리얼에도 전용 기능은 없다. 언리얼이었다면 목표 지점에 Trigger Volume + 블루프린트로 회전 비교를 했을 것이고, 이 ADR의 A안과 같은 접근이다. 유니티에서는 판정 로직을 MonoBehaviour 밖(Core asmdef의 순수 C#)으로 빼서 에디터 없이 테스트한다는 점이 다르다(언리얼의 Automation Test보다 훨씬 가볍게 돈다).

## 결과 / 트레이드오프
- 좋아지는 점: 판정이 예측 가능하고 단위 테스트로 고정된다.
- 감수하는 점: "목표와 다른 배치로 우연히 같은 그림자"는 인정되지 않을 수 있다.
- 재검토 시점: 플레이테스트에서 "맞게 보이는데 안 된다"는 피드백이 반복되면 C(하이브리드)를 검토한다.
